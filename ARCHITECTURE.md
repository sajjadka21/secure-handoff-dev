# Architecture

## Desktop integration status (Phase 3 implementation)

`apps/desktop` is the Tauri v2 + React/TypeScript shell. Its Rust crate depends on the existing `crates/clipcore`; it does not reimplement cryptography. `src-tauri/src/lib.rs` is a narrow typed command boundary. It keeps `DeviceIdentity` and `TrustDb` in Tauri managed Rust state and exposes only non-secret device metadata, preferences, activity metadata, diagnostics, and explicit revocation.

At startup, the app creates the OS app-data directory, loads an existing identity or creates one only on the explicit `Missing` result, and fails startup on corrupt/locked/denied storage. Windows uses the existing Credential Manager adapter; Linux uses Secret Service. The trust DB is SQLite in OS app data; settings and metadata-only activity are JSON there. No payload or identity secret is persisted in those files.

The desktop now creates volatile issuer invitations with a LAN listener, renders/imports the real canonical QR payload, runs QR-bound Noise XX, displays transcript SAS, and commits trust only through the existing bilateral state machine. A separate bounded LAN listener accepts fresh Noise sessions and calls the trust/revocation gate before reading the text envelope. Outgoing transfers create a fresh session and verify the selected peer key. Received text is emitted to the UI in memory; activity retains metadata only. The endpoint is currently shared/entered manually and there is no LAN discovery or cross-platform route selection. Privacy Pause gates pairing, send, and incoming delivery. Tray actions are wired, but native tray behavior and the two-app end-to-end flow have not yet been manually verified.

Frontend dependencies are not a security boundary. Rust validates settings and device IDs; cryptographic material stays in `clipcore`/OS storage. Clipboard operations use the Tauri clipboard plugin only after user action and are not monitored in the background. Diagnostics are constructed from an allowlist; clipboard/Compose content, secrets, raw DB rows, paths, and IP history are excluded.

## Components and trust boundaries
`crates/clipcore` owns identity data types, versioned message envelopes, handshake orchestration, route interfaces, bounded QR parsing, pairing state, trust/revocation logic, and secure-store adapters. The Phase 3 desktop shell supplies explicit clipboard actions, pairing UI, tray wiring, and LAN text transfer around that core; it does not implement clipboard monitoring, files, discovery, or relay. `apps/android` is a Kotlin/Jetpack Compose client; `crates/android-bridge` exposes narrow JNI calls. Kotlin owns lifecycle, UI, Google Code Scanner invocation, clipboard access, and Android Keystore wrapping. Rust remains authoritative for identity validation, QR parsing, Noise, SAS, pairing controls, trust/revocation, and encrypted application messages. The Android source now wires QR joining, authenticated bilateral pairing controls, the existing SQLite trust DB, revocation, foreground LAN TCP receive, and per-transfer LAN text send into that core. Compose and explicit clipboard transfer use the same text envelope. This integration has not yet passed hosted Android compilation or runtime testing, so the behavior is implemented in source only. No core protocol is reimplemented in Kotlin. The PWA has a separate browser-only implementation and threat model; it does not claim to share native key storage or background behavior. A signaling service may exchange rendezvous metadata only; peers encrypt content before any transport.

## V1 platform priority and Android boundary
V1 prioritizes bidirectional Windows ↔ Android first, Windows ↔ iPhone/iPad second where foreground browser APIs permit, and Windows ↔ Windows as a secondary low-cost pairing. The first Android transport slice is LAN TCP only. Eventual route targets are LAN, Wi-Fi Direct where reliable, WebRTC direct, then capped TURN; BLE is only a discovery/bootstrap option where useful. Route availability never implies trust and never replaces the existing QR/SAS and Noise security checks. Windows ↔ Windows Phase 3 E2E remains OPEN because no independent second Windows runtime was available; this is a validation environment limitation, not a product failure finding.

The Android identity foundation now generates and validates the Rust `CBID` v1 record through `crates/android-bridge` using `jni` 0.21.1. After the encrypted record is committed, JNI installs the validated `DeviceIdentity` into a process-local Rust slot; it refuses to replace a different live identity. Kotlin wraps the 70-byte record with Android Keystore AES-256-GCM, a fresh 96-bit provider-generated nonce and 128-bit tag. The 136-byte envelope carries the version and public key; authenticated data binds the application ID, record version, wrapping-key alias and public key. The ciphertext lives in app-private `noBackupFilesDir`; Android backup is disabled at the application boundary. Existing malformed, missing, unwrappable, or mismatched material fails closed without silent identity replacement. **Memory caveat:** the current JNI interface returns/passes a short-lived Java `ByteArray` containing the identity record during wrapping/unwrapping; the Rust input copy is zeroized, and Kotlin calls `Arrays.fill` after use, but the JVM/provider may make copies that cannot be reliably wiped. This is an explicit residual risk for security review, and the JNI bridge is not itself secure storage. Keystore hardware backing varies by device, so no hardware-backed claim is made.

Android stores the clipcore trust database under `noBackupFilesDir`; Kotlin receives bounded public trust metadata and cannot make trust decisions. The app scans an issuer QR through Google Code Scanner or accepts a user-pasted hex encoding, then Rust validates and joins it. The joining side verifies the Noise issuer key against the QR key, displays transcript SAS, and waits for explicit approval before exchanging authenticated PAIR_CONFIRM/PAIR_ACK. A foreground TCP receiver binds only to a selected private/loopback address and an ephemeral port; the listener stops when the Activity leaves the foreground. Each send/receive uses the existing trusted LAN session and envelope; received content is displayed in the active receive surface and copied only on request. Compose and explicit clipboard reads feed the same send path. Activity is bounded to metadata-only typed events; diagnostics use an allowlisted serializer. These integrations are source-only until hosted Android build and emulator/device validation passes. No content history or automatic clipboard writes are implemented. The JNI identity record briefly transits a Java byte array for Keystore wrapping; best-effort buffer clearing cannot guarantee removal of all JVM/provider copies.

The CLI text prototype still has an ephemeral identity mode for the Phase 1 process-exchange demonstration. Phase 2 adds `DeviceIdentity` with a strict 70-byte `CBID` v1 record (magic, big-endian version, 32-byte X25519 secret, and recomputed 32-byte public key), plus explicit `IdentityManager` create/load/replace operations. Windows stores this blob in Credential Manager with `CRED_PERSIST_LOCAL_MACHINE`; Linux uses Secret Service with fixed non-identifying attributes and the blob only as the Secret value. Neither adapter falls back to a plaintext file. Runtime Secret Service/Windows OS fault-injection coverage remains incomplete.

`TrustDb` uses bundled SQLite with WAL and transactional trust/revocation operations. It stores identity metadata, labels, trust status, protocol floor and revocation reason/timestamps only; no content or history. SQLite does not encrypt this database, so public identity metadata and local labels are visible to a local user with file access. The desktop places the database under the OS application-data directory and relies on OS profile permissions. Private identity bytes are never written to this database. Revocation denylist insertion and trusted-row deletion share a transaction; in-process sessions are invalidated after commit. `needs_repair` rows cannot authorize application data. Recovery requires revoke and fresh pairing.

Pairing v1 implements canonical QR codec and a volatile one-invitation issuer, then QR-bound Noise XX, issuer static-key verification on the joining side, transcript-derived SAS display, and Noise-authenticated confirmation/ACK messages. Trust is committed independently at each endpoint after its local predicate; final-window transport loss may leave asymmetric local trust. Observed local failures quarantine a previously committed record. This is deliberately not distributed atomic commit.

The implemented desktop dependencies and current validation evidence are listed in `apps/desktop/package.json`, `apps/desktop/src-tauri/Cargo.toml`, and `TEST_PLAN.md`. Android dependency versions and validation evidence are listed in `apps/android` and `TEST_PLAN.md`; source documentation is not runtime evidence. WebRTC compatibility remains unselected implementation work.

## Dependency direction
OS shell / platform adapters → stable Rust core API → `SecureTransport` adapter. Route selection cannot access plaintext or keys and cannot disable peer pin checks, Noise authentication, envelope version checks, or payload limits. Server signaling can exchange opaque rendezvous data only. Never use Cloudflare R2.

## Routes and Route Manager
Planned adapter contract: capability probe, `available()`, estimated setup latency/bandwidth/cost/power, `connect(peer, limits)`, send/receive encrypted frames, cancel, and structured failure. `RouteManager` ranks candidates with deterministic policy: reject unsupported/insecure routes; prefer direct LAN; then supported Nearby Connections; then platform Bluetooth/BLE route when justified; then direct WebRTC; then Cloudflare TURN as an opt-in last resort under the user's hard cost cap. It measures actual setup and falls back only by closing the failed session and establishing a fresh Noise XX session on the next candidate, revalidating the same pinned peer key and protocol floor. V1 never rebinds a live Noise session or reuses its cipher state, counters, nonce, transcript, or partially written ciphertext. Payload size, availability, battery, bandwidth, setup reliability, user preference and configured cost ceiling influence selection. Route labels and reason codes are surfaced to users. Silent route changes are logged only as sanitized metadata.

The current working desktop transport is LAN TCP with a fresh Noise XX session for each transfer; no route manager or discovery is implemented. Later LAN discovery must be untrusted hints (mDNS/UDP discovery is not identity). All unauthenticated discovery mechanisms use rotating random ephemeral IDs, never persistent IDs, static public keys, fingerprints, account identifiers, or names. Nearby Connections is Android-specific and remains an optional route, not the only Android pairing path. Bluetooth/BLE is native-platform-specific, with payload/throughput limitations to measure. WebRTC peer-to-peer data channels require ICE/STUN and signaling; WebRTC deliberately does not define signaling. Cloudflare signaling should coordinate short-lived offer/answer/ICE exchange through Durable Objects WebSockets. Cloudflare TURN is an optional relay fallback, never a plaintext decryptor. End-to-end application encryption remains mandatory atop every path.

## Relay and storage boundaries
Signaling records in memory only: random room token, two connection slots, creation/expiry time, rate counters, and opaque WebRTC signaling fields. No user text, files, images, clipboard history, durable queues, object storage, or R2. Short-lived in-memory relay buffers are bounded by message, session, byte, concurrency, and age limits and are erased on disconnect/expiry. Durable Object persistent storage (SQL, KV or other) must not be used for application content or durable rendezvous history. A separate global aggregate egress meter may persist only time-bucketed byte totals/reset metadata for hard cost stops, never room tokens, peer IDs, IPs, contents, or transfer history. Workers return explicit quota/availability failures; no hidden failover that can trigger paid usage. Budgets are verified against live official pricing/limits before any deployment, hard caps stop relay at the configured threshold, and TURN credentials are short-lived and rate-limited.

Initial proposed relay product caps for a future deployment: exactly two peers per rendezvous; 8 KiB signaling frame; 64 KiB opaque relay frame; 10-minute session lifetime; 10 MiB aggregate application ciphertext per relay session; no durable queue; 128 KiB per-peer in-memory send/backpressure buffer. Apply a provisional source-IP throttle of 10 rendezvous creation attempts per 10 minutes and 3 TURN credential issuances per 10 minutes; IP is abuse metadata, never identity. Hard application/account circuit-breaker caps start at 512 MiB/day and 5 GiB/month of TURN egress. The meter may hold only aggregate time-bucketed byte totals and reset metadata. At a cap, fail closed for relay/TURN until the next budget window or operator action, with a clear client error. TURN is opt-in and last-resort. Never assume Cloudflare's free tier for product safety; hard byte/cost caps apply regardless of allowances. Recheck pricing immediately before deployment. If usage cannot be measured and capped reliably, disable relay rather than risk silent paid usage. These are conservative proposed product caps, not Cloudflare plan limits.

Cloudflare's current official pages describe allowances differently: the [Realtime TURN service overview](https://developers.cloudflare.com/realtime/turn/) says TURN is free when used together with Realtime SFU and otherwise costs $0.05 per real-time GB outbound from Cloudflare to the TURN client. The [TURN FAQ](https://developers.cloudflare.com/realtime/turn/faq/) and [Realtime pricing page](https://developers.cloudflare.com/realtime/sfu/platform/pricing/) state $0.05/GB egress and a shared first 1,000 GB/month free tier across SFU and TURN. This architecture does not depend on that allowance; enforce configured hard caps and re-verify the deployed plan's billing immediately before launch.

## Content/file transfer design (future)
Envelope carries message ID, monotonically increasing per-direction sequence, protocol version, type, and bounded payload length. Text is UTF-8 with an explicit subtype (`plain`, `url`, `code` metadata), byte size, and optional language label; labels are hints, never executable interpretation. File offer metadata contains opaque transfer ID, basename, MIME hint, declared byte length, chunk size/count, and SHA-256 digest. User accepts before data is written. Each independently authenticated chunk carries transfer ID, index, length and content; receiver checks exact expected index/size and running/final digest, then commits an atomic rename inside an app-owned receive directory. Limits are checked before allocation and while streaming. Cancel unlinks only the app-created temporary file. No extraction, execution, overwrite, path component, symlink traversal, or sender-supplied destination path. Resume is postponed until restart-safe authenticated checkpoints, replay windows, and partial-file cleanup pass adversarial tests.

Future clipboard events carry `clipboard_event_id` (random 128-bit), authenticated `origin_device_id` (32-byte identity ID), subtype, and UTF-8 payload. Keep at most 4,096 dedup IDs for 10 minutes in memory. Mark inbound events before OS write and use platform-origin tokens/generation to prevent creating a new local event; do not depend only on text equality. Multi-device forwarding preserves origin/event IDs and checks the dedup cache. This is design-only; no clipboard adapter exists.

## Failure handling and diagnostics
Typed error classes: route unavailable, peer identity mismatch/revoked, incompatible protocol, authentication/tamper, replay/order, size/rate limit, user cancel, timeout, platform capability absent, clipboard permission/lifecycle denial, and service quota. Recovery hints are safe and specific. Diagnostics contain version, OS/backend, route attempts/results, elapsed timing buckets, negotiated protocol/crypto suite, payload byte count bucket and sanitized error code; never text, file names/paths, content hashes, key material, QR secrets, IP history, or raw signaling. Diagnostics are local by default and user-controlled export is redacted and previewed.

## Help & Guide architecture
Help content is structured data keyed by task/platform/route/capability/error code. Guided steps use small original SVG illustrations, numbered actions, expected UI states, and platform-specific troubleshooting. A connection-method matrix is generated from the same capability IDs used by runtime diagnostics so explanatory UI cannot overstate support. Each help entry states supported platforms, current device availability, route selection reason, limitations, and recovery. Accessibility requires keyboard operation, screen reader labels, contrast, reduced-motion behavior and non-color state cues.

## Platform constraints
- Windows: future native adapter must use documented clipboard listener/change APIs, suppress self-originated loops, and inspect Windows clipboard sequence/source/privacy metadata when available. Exact API implementation awaits official platform validation.
- Linux: X11 selection ownership and Wayland compositor-mediated `wl_data_device` behave differently. Wayland data sharing is compositor-mediated; global clipboard-manager access may require a compositor-specific protocol such as staging `ext-data-control-v1`, and cannot be assumed on all compositors. Probe the actual session/compositor and advertised protocols at runtime, report unavailable states, and use a user-initiated fallback. Never pretend X11 monitoring works in Wayland.
- Android: from Android 10 (API 29), clipboard content is readable only by the focused app or default IME. Clipboard APIs and lifecycle/background rules constrain reliable receiving too; background services do not override clipboard privacy. Quick Settings/share actions explicitly initiate transfer; no workaround or hidden polling.
- Android LAN: current source targets SDK 36 and uses ordinary TCP sockets on the active private Wi-Fi/Ethernet interface. It does not request `NEARBY_WIFI_DEVICES`, which covers nearby Wi-Fi APIs rather than this TCP socket flow. Android 16 local-network protections can be enabled for testing; Android 17 requires `ACCESS_LOCAL_NETWORK` for apps targeting API 37+, or supported system-mediated access. Before raising target SDK, implement and test permission rationale, denial/revocation and both outbound and accepted TCP. The Android path is not runtime validated yet.
- PWA: secure context plus browser-specific permissions/user activation; no unrestricted background clipboard monitor. Service Worker is not a clipboard daemon.
