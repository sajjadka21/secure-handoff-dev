# Threat Model

## Assets
Clipboard/file contents, device identity private key, peer trust records, transfer file integrity, pairing decisions, availability and privacy metadata (IP, timing, usage). Security requires confidentiality/integrity and correct user intent; availability cannot be guaranteed.

## Adversaries and assumptions
Consider malicious nearby devices, LAN/Wi-Fi attackers, spoofed discovery, passive/active network observers, malicious relay/operator, replay/injection/modification, compromised untrusted peer, malformed/high-volume traffic, clipboard-monitoring malware, stolen unlocked device, dependency compromise, and accidental user pairing. Assume OS/kernel, cryptographic library implementations, randomness, build host and trusted device endpoints are not compromised. Native local malware with same-user access may read clipboard or unlocked secrets; this design does not defend against that.

## Security controls
- Noise XX v1 authenticates pinned static keys, provides ephemeral DH and encrypted transport records; QR + dual SAS confirmation protects first-contact identity from MITM.
- The transport route never decides trust or encryption. Strict protocol floor/prologue and envelope version prevent silent downgrade.
- Noise AEAD tags detect ciphertext tampering; its transport counters reject replay; envelope sequences reject out-of-order or duplicate logical data.
- Bounded framing, UTF-8, explicit length, limits, state machines, deadlines, and reject-closed behavior mitigate malformed input and resource exhaustion.
- Revocation invalidates trust locally and terminates active sessions.
- Pairing requires both users to verify the same transcript-bound SAS and send authenticated confirmation/acknowledgement messages. Each endpoint commits only when its local protocol predicate passes; the network cannot atomically commit both peer databases. A final-window transport failure may leave asymmetric local trust. An endpoint that observes failure reports pairing incomplete, disables any locally committed record as `needs_repair`, and requires explicit revoke/re-pair. The non-trusting peer rejects a subsequent session before application data. No automatic trust repair is allowed.
- Discovery emits rotating random ephemeral identifiers only; static device IDs, public keys, fingerprints, stable names and account identifiers are withheld until authenticated peer-key validation.
- Route fallback closes the old Noise session and performs a new XX handshake against the pinned identity. V1 never migrates or rebinds a live cipher state.
- Content-free logs; user-mediated receive; safe temporary paths; no execution/extraction; no persistent server content.

## Explicit limitations and risks
The preceding Phase 2 validation record in `TEST_PLAN.md` reports completed Windows 2022 and Ubuntu 24.04 CI quality runs, four bounded Linux fuzz runs, dependency/license checks, SBOM, and Gitleaks. Phase 3 adds a Windows/Linux Tauri desktop client, QR/SAS pairing integration, local trust UI, and encrypted one-shot LAN text transfer, but app-level two-instance validation, current Ubuntu Phase 3 build/runtime evidence, screenshot QA, and native tray testing remain open in this pass. Native Credential Manager/Secret Service fault injection remains incomplete. Independent crypto/state-machine review, cross-implementation vectors, side-channel evaluation, longer fuzzing, and release hardening remain open. Static X25519 identity has no separate signing key; `snow` is a dependency, not a formal security audit. The historical CLI demo binds TCP and does not implement discovery. SQLite trust metadata is not encrypted by SQLite; rely on OS profile access controls and do not store private keys or user content there. A local user with process access may inspect a live private key. A malicious already-trusted peer can send unwanted content; later consent/limits still matter. Device compromise can steal current keys and clipboard. The PWA shares browser-origin risks and does not inherit OS key isolation.

## Abuse/cost controls (planned relay)
Anonymous session tokens are random, short-lived, single-use, and bound to two peers and app protocol. Enforce connection/IP/session-token rate limits; max two peers/session; tight WebSocket frame cap; setup timeout; ≤10-minute session; per-peer bytes and daily anonymous quota; bounded in-memory buffers; backpressure; close on invalid handshake; circuit breaker, abuse reporting, and operational alerts. Product hard application/account byte and cost caps are enforced before TURN credentials/session issuance; stop at cap rather than rely on billing alerts or a free tier. TURN is opt-in and last-resort. On quota exhaustion return a clear error and offer local retry. As checked 2026-10-06, Cloudflare's TURN service overview says $0.05 per real-time GB outbound from Cloudflare to the TURN client when not used with Realtime SFU; the TURN FAQ and Realtime pricing page currently state a shared 1,000 GB monthly free tier for SFU and TURN, then $0.05/GB egress. These pages phrase the allowance differently. Product safety never assumes it; recheck the actual plan/account pricing immediately before deployment and fail closed rather than silently incur relay costs. Official Workers Free currently lists 100,000 requests/day and 10 ms CPU; Paid CPU limit up to 5 minutes (check configured limits), and request-body sizes depend on account plan. Durable Objects hibernatable WebSockets support up to 32,768 connections per object, but per-message product caps must be set far lower; no current 32 MiB WebSocket message limit is relied upon here. Never persist content or use R2.

Official verification sources (checked 2026-10-06): [Cloudflare Realtime TURN service overview](https://developers.cloudflare.com/realtime/turn/), [TURN FAQ](https://developers.cloudflare.com/realtime/turn/faq/), [Realtime pricing](https://developers.cloudflare.com/realtime/sfu/platform/pricing/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Durable Objects WebSocket API](https://developers.cloudflare.com/durable-objects/api/state/), [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/).

## PWA threat-model differences
PWA code executes within browser origin/storage/extension model, may be updated remotely, and clipboard access is permission/user-activation/browser-policy constrained. Browser storage may be cleared or backed up according to browser behavior. It lacks native keystore guarantees and is exposed to same-origin script/XSS and service-worker supply-chain risk. Require strict CSP, no third-party script, pinned dependencies, explicit foreground user gestures, no content telemetry, and separate review; never market it as equivalent to native background sync.

## Discovery and route metadata
LAN/mDNS/UDP, Nearby, Bluetooth/BLE and public signaling are observable and may be spoofed. An observer may correlate IP address, radio address, timing, route use, packet size and availability even when the app payload remains encrypted. Rotating random ephemeral discovery IDs reduce app-level stable correlation but do not hide radio/MAC/IP metadata. Discovery data is only an endpoint hint. A peer becomes associated with a trusted identity only after Noise authenticates the static key and policy checks it against the trust database.

## Key-storage failure assumptions
OS key stores reduce exposure at rest but do not protect a secret while the trusted process is unlocked and using it, against same-user malware, kernel compromise, malicious endpoint, backups misconfigured by the OS, or implementation mistakes. Windows local persistence must not roam. Android backup exclusions must cover cloud and device-transfer paths; if an encrypted identity is restored without its Keystore wrapping key, treat identity as lost and require re-pairing. Linux Secret Service metadata can be unencrypted and must not include identity fingerprints or other stable identifiers.
